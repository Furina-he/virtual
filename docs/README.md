`active/archive` 登记项必须存在，实际项目文档必须已登记；`retired` 在当前工作区必须不存在，也不能成为有效本地链接目标。它是精确的历史路径例外，不是有效入口。旧交接文档目前为用户未提交删除，保留该状态，不恢复、不混入其他提交；增量审计不能把 Git 中未变化的旧退役 blob 误当本任务恢复。不得把“忽略所有不存在文档”当退役策略。

信息只有一个可变来源：任务状态/回执/评审在任务卡，最近架构认可的阶段/回归在项目验收快照，现行需求/实现/接口在各自规范，专题证据/候选方案在批准的任务章节，历史事件在追加日志。其他文件只链接，不复制任务阶段或再维护一份最新成绩。`content/` 指导书/具名拓扑、`assets/` 测试布局及 `resources/` 许可证不纳入此项目登记表，但仍遵守命名/链接及任务新增准入，不能换目录绕过。

需求以 PRD 为准，实现以已批准的技术设计与公共契约为准。发生冲突先报告架构负责人，不能在代码里绕过，也不能以历史记录重新定义现行接口。`PRODUCT.md` 是 PRD 的派生设计上下文，不是第二份需求源。

## 命名与更新

1. 文件名用主题，不以数字开头，不再用 `01-`、`02-` 等排序前缀；项目编号 `SD-22`、任务编号和标题内序号可以保留。入口文件保持 `README.md`。
2. 现行规范放在 `docs/`，失效评审、旧接口建议和逐轮日志放在 `docs/archive/`。归档写明原日期/提交，并链接现行依据；不删除唯一决策、失败或验收证据。
3. 当前任务状态只在执行计划的任务标题维护；执行结果/验收收据留在该卡。项目状态的任务入口只存任务 ID/链接，不能复制阶段；回归记录必须注明实际日期、代码/工作区来源和证据，不能把当前 HEAD 或方案通过当旧测试重跑。
4. 改名和移动时同时修复 Markdown 链接、图片和反引号里的 `docs/*.md` 引用；文档使用仓库内相对链接，不引入机器专属路径作为规范入口。
5. 改契约前明确已批准的联动范围；交付回执填写 `SyncImpact`，说明已同步的规范/schema/内容/测试，或不受影响的理由。工具不能判断语义一致，不要求为通过检查触碰无关文件。
6. 完成更新后运行 `pnpm docs:lint` 和差异检查。已验收的基础能力仍是原命名/本地目标检查；新增治理门禁的验收以 [GOV-01](执行计划.md#gov-01) 及 [GOV-02](执行计划.md#gov-02)、[GOV-03](执行计划.md#gov-03) 补正回执为准，完整放行能力尚未启用，参数/自测通过不能替代架构验收。不认证身份、证据真实性、锚点语义或产品验收；当前检查只作辅助，仍须架构核对差异和证据。

## 文档校验操作说明

<!-- docs-usage:start -->
以下是检查操作方法，不是任务状态或最新成绩副本。已验收能力仍只按上一节第 6 条声明；参数与示例存在不代表新门禁已经通过架构验收。

**推荐顺序**：领取前记录完整 HEAD、任务卡和用户已有改动；完成获准改动后先查当前工作区，再选择性暂存并审计暂存树，提交后用最终 SHA 审计交付提交。工具只读，不修复文件、不暂存、不提交、不联网、不自动写报告。

```powershell
pnpm docs:lint
node tools/docs-lint.ts "<可选检查目录>"
node tools/docs-lint.ts --task "<任务ID>" --base "<领取时完整SHA>" --staged
# 选择性提交后，把实际交付 SHA 作为目标；不要把 SHA 写回自身提交或 amend。
node tools/docs-lint.ts --task "<任务ID>" --base "<领取时完整SHA>" --commit "<交付SHA>"
```

- 无模式参数时是 `static`：读取磁盘上的当前文件。可选目录保留原命名/本地链接的目录及后代检查范围；登记与任务结构始终以所在 Git 仓库为准，不能换目录绕过治理。
- `--staged`：审查指派基线到实际暂存树的差异，不混入未暂存的修改/删除；空暂存返回 `STAGED_EMPTY`，`git add -N` 也不把文件变成交付内容。基线须是当前 HEAD 的祖先。
- `--commit <SHA>`：只读取目标提交，目标必须是基线的后继提交，不以当前工作区替换目标。两种增量模式都必须给 `--task` 和 `--base`，不能同时使用；无模式时不能携带这两个参数。
- 授权只读基线中的本任务 `task-policy`。使用已记录的完整领取 SHA，不用会变化的 `HEAD` 代替；执行回执的 `ClaimBase` 必须等于解析后的基线。新增、删除及重命名两端分别需要明确 `add`/`retire` 授权，新增并不隐式放开登记和导航编辑。
- 首次增量授权要求基线卡为 ☐、`ClaimBase=null`，评审为 `Decision=pending` 且 `ReviewedCommit/Date=null`；已领取、已交付、已评审或阻塞卡不能成为新的领取基线。进行中卡的静态检查仍可正常通过，同一未正式交付工作可沿原 ClaimBase 连续提交；历史目标审计只读当时的目标树，不用当前工作区或后续评审替换它。
- 首次领取使用未领取任务的原指派基线；恢复同一任务仍用原 ClaimBase，当前 HEAD 只作为过程记录。途中交付、已领取或已验收卡不是新的开工授权。以下操作说明是正确使用契约，具体强制检查的验收范围以任务卡为准，不因旧候选实现返回绿色就允许悄悄重定基线。
- 增量审计不替代静态检查：它不把未变化的退役旧 blob 当作恢复，也不证明所有未变化文档可用。具名块仅允许内文变化；本卡授权/验收/架构评审、其他卡及区块外原文仍受保护。归档历史只能保留完整 CRLF/LF 规范化前缀后追加，改写例外只来自基线的 `history_rewrite`。
- 故障注入只在最小隔离 Git fixture 中做。真实工作树只运行合法检查和本人交付审计；遇到用户已有删除，报告问题或保留未暂存状态，不擅自恢复或混入提交。

**输出与定位**：成功退出 `0`，有问题退出非 `0`。默认 stdout 为数量/模式及增量目标摘要，stderr 每条问题包含 `文件:行号`、稳定错误码和字段/基线说明，例如：

```text
<文档数> Markdown files; <问题数> issues (staged)
task=<任务ID>; base=<已解析的基线SHA>; target=index; changes=<变更路径数>
docs/执行计划.md:<行号>: [TASK_SCOPE] 仅本人执行块和首次开工状态可改，授权/验收/评审/其他任务受保护
```

机器消费时直接调用 Node 并加 `--json`，避免包管理器的命令横幅混进输出。成功、规则失败、参数错误和 Git 错误都返回一个合法 JSON 对象；stdout 不混入文本，包含 `mode/task/base/target/files/changes/issues`。下面仅示意核心字段，不表示一次项目检查结果：

```powershell
node tools/docs-lint.ts --task "<任务ID>" --base "<领取时完整SHA>" --staged --json
node tools/docs-lint.ts --task "<任务ID>" --base "<领取时完整SHA>" --commit "<交付SHA>" --json
```

```json
{
  "mode": "staged",
  "task": "<任务ID>",
  "base": "<已解析的指派SHA>",
  "target": "index",
  "issues": [
    {
      "code": "TASK_SCOPE",
      "file": "docs/执行计划.md",
      "line": 1,
      "message": "<具体字段、受保护范围和基线说明>"
    }
  ]
}
```

**常见错误处理**：先根据 `file/line/message` 查看实际差异，再在授权内修正并重新检查；不能自改当前白名单、删掉历史失败或放宽任务验收来消除错误。

**Markdown 与本地目标范围**：以下是本卡工具的使用边界，不是完整 Markdown 引擎或已启用门禁的验收声明。

- 支持单行标签/目标/可选标题的 inline 链接、图片，以及 full `[文字][标签]`、collapsed `[标签][]`、shortcut `[标签]` 和对应图片引用。引用定义仅支持顶层单行形式，放在原始行的真实逻辑起点、空行后或连续定义中；标签按大小写与空白规范化。段落内不成立的定义明确报 `LOCAL_LINK_UNSUPPORTED`，不能因上一行注释或前导行内代码遮蔽为空就获得定义或导航资格。未使用的定义也检查目标，但定义本身、图片和代码示例不构成新增文档导航；无定义的普通单行/多行方括号保持普通文本，明确 full/collapsed 未定义或重复定义报错。
- fenced 示例按 marker 类型及最小关闭长度遮蔽；backtick fence 的 info 不能含 backtick。段落/块状态与等长遮蔽独立：段落内有效跨行注释的独占续行、关闭行不结束段落；真实空行、横线和 Setext 标题等块边界才改变后续代码/定义资格。有序列表的合法编号为 1-9 位数字；新列表须有非空内容才能打断普通段落，有序起始编号还须为 1；真实块起点可用其他编号或空条目，同层后续条目仍识别为边界，不能把普通编号/空标记文字误当代码跨度的终点。行首独立 HTML 注释是块而不是段落内注释；不在同一段落闭合的 inline 注释开启符保持字面文本，不能隐藏后续真实链接。顶层确定的四列/tab 缩进代码、fenced、注释和行内代码不贡献导航；横线/Setext 后的代码也不例外，普通段落及基础单层列表续行不能仅因四空格被隐藏。行内代码与多行标签均止于同一实际块边界，行内代码里的具名 `docs/*.md` 路径仍作契约引用检查，只有登记表真正 path 声明单元格可豁免退役路径。JSON 元数据和授权区块继续按原文读取，CRLF/LF 与原文位置不因示例遮蔽而改变。
- 本地目标支持库内相对/根相对路径、UTF-8、URL 编码、angle 目标中的空格、平衡括号及现有反斜杠转义。查询/片段先按原约定剥离，URL 编码再解码；纯锚点、查询、外部协议与原始 `//host` 不验证目标或锚点语义。路径须与库内真实名称一致；库外路径、原生/编码网络路径、尾点/尾空格、控制字符、Windows 保留名及文件系统/Git 别名不放行。静态读取源文档和目标前逐前缀检查，不跟随 symlink/junction/gitlink，也不读取库外文件。
- 多行 inline/image 标签、full/collapsed 的显示或引用标签、已定义 shortcut 标签、目标/标题及引用定义返回 `LOCAL_LINK_UNSUPPORTED`，不能用作导航。标签检测沿当前实际块到配对结束处，不限两行；真实空行/标题等中断后的方括号不拼成跨块链接。标题续行仅在前定义尚无标题、续行具备匹配关闭符且关闭行仅剩空白时成立；已有单行标题后的普通段落、未闭合或关闭行仍有正文的引号/括号文本不误报。单层引用/列表内的有效跨行行内代码和注释使用剥离一层前缀后的相同段落边界，不贡献导航；引用段落中的普通无前缀续行不因零缩进重置上下文，容器内真空行/标题等也不能被跨度吞掉。引用/列表容器及其续行中的定义（含嵌套候选）统一明确拒绝，不加入定义表；后续 full/collapsed/shortcut/image 不能靠遗漏定义获得绿色或导航资格。普通无定义容器文本保留，原已支持的单行可见链接继续检查目标。非块起点的定义、本地 HTML `href/src` 及无法明确解析的嵌套列表/引用代码容器也返回 `LOCAL_LINK_UNSUPPORTED`。目标中的 HTML entity 暂不解码，返回 `LOCAL_PATH_UNSUPPORTED`，改用 URL 编码。更复杂的容器/HTML 与完整 Markdown 渲染语义不在本卡覆盖内；不要据一个绿灯宣称通用语法、人工身份、审批或产品验收通过。

## 新增与交付闭环

1. 每张任务默认不新增、改名、移动或退役文档。申请须说明既有文档为何不能容纳、唯一职责、完整登记字段、路径及替代/关联关系；架构先在指派基线授权，再实施，不能执行者自改当前清单就视作获批。
2. 新文档与本表登记、导航/引用修复、必要的旧文档归档或退役同提交完成；未获批的临时结果放任务回执/已批准原始证据目录，不新造 Markdown 摘要。旧文件退役及迁移不等于丢弃唯一证据。
3. 一个共享工作树只运行一个写入任务，架构在执行期间只读。领取时记录 `ClaimBase`/已有用户改动；执行者只改变本任务执行区和首次开工状态，不改变本卡授权/验收条件、其他任务或架构评审区。
4. 执行提交同时交付本卡回执、最小过程日志和获准成果；最终 SHA 提交后报告，不要求写进它自身提交。没有影响的规范/项目快照不为“同步”而改。
5. 架构验收在同一评审提交写 `ReviewedCommit`/结论、改变任务状态，并处理专题中独立的待验收标签和必要的验收快照/下一授权。专题只引用卡上的评审/授权，不保留另一份实时状态；归档中的旧“待验收”保留为当时事实。
6. 历史只追加，错误通过带日期/依据的勘误纠正；引用机械迁移等例外须列入授权。自动门禁只检查机械覆盖/差异/收据，审批真实性、语义同步与产品验收仍由架构核对。

## 分支生命周期

- `main` 保留已评审的集成基线；不是“正式发版已验收”的证明。未通过本次出口的整合工作保留在一个活动分支，避免继续拆出同任务的长期分支。
- 开始任务前明确任务卡、改动边界和验收命令。公共能力不得按项目编号做特例，内容分支不得覆盖另一方的共享 catalog/manifest/许可证。
- 合入 `main` 前检查干净/已隔离的用户改动、差异、类型/lint/文档/内容/资产校验、单元与真实金标准，以及本次变更相关的完整 E2E/流程证据。已知失败未解决时不以“清理分支”为由推进主干。
- 先用 `git merge-base --is-ancestor` 核实任务分支已进入保留的目标分支，再删除；优先 `git branch -d`，不使用强制删除掩盖独有提交。
- 绑定 worktree 的分支先检查 tracked、untracked、ignored 文件与运行进程。录屏、原始红/绿日志和哈希索引先独立保留并逐文件校验；可复建依赖/编译缓存才可删除。
- 不自动推送、重写历史或创建更多备份分支。分支删除只代表工作已归入保留分支，不代表任务或里程碑验收完成。
