## 维护规则

1. 一条信息只在一个地方维护：状态和结果写进执行计划，设计结论写进技术设计，其他文档只放链接。当前成绩只出现在执行计划"当前状态"的回归基线，README 和规范文档不写进度。
2. 改需求或改设计，先改文档再改代码；发现冲突写进执行计划的"待决策"。改了设计结论就同步更新该文档的版本/日期行。
3. 新增文档要先说明为什么现有文档放不下，并在本页清单登记。临时结果放 `build/`，不写成新的 Markdown。
4. 文件名用主题命名，不以数字开头（`SD-22` 这类编号可以保留）。改名或移动时同步修复链接。
5. 归档文档保留原日期和原始失败，只追加，不改写。
6. 改完文档运行 `pnpm docs:lint`，检查命名规则和本地链接、图片目标是否存在。

## 分支与证据

- `main` 是已集成的基线，不代表正式验收；尚未通过出口的工作留在唯一的活动分支。合入 `main` 前要求静态检查、单元/金标准和相关 E2E 通过；已知失败没解决时不合入。
- 删分支前先用 `git merge-base --is-ancestor` 确认已并入，用 `git branch -d`，不强删、不自动推送、不改写历史。
- `build/` 被 Git 忽略，但里面的录屏、原始失败日志、原生归因证据和哈希索引不能覆盖或删除。SD-22 旧证据在 `build/retained-sd22/`。`node_modules/`、`out/`、`dist/`、`test-results/` 可以重建。
- `assets/kicad/` 仍被测试读取；`content/` 里的指导书、参考拓扑和第三方许可是运行时与测试契约，不当作重复文档处理。
